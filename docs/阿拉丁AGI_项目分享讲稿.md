# 阿拉丁AGI 项目分享讲稿

> 面向：老师与同学  
> 场景：课程作业验收 + 生产机产品演示  
> 推荐时长：8 到 10 分钟  
> 在线演示：https://aladdin.myanext.com/

## 形式建议

我建议课堂分享用 **PPT 为主，Markdown 讲稿为辅**。

PPT 的好处是节奏清楚：老师能快速看到“需求是否落地、链上是否真实、生产是否可访问”；同学能跟着页面和架构理解实现路径。Markdown 更适合作为自己的讲稿和答辩备忘，里面可以放完整话术、演示步骤和可能被问到的问题。

本稿对应 11 页 PPT，每页讲 40 到 60 秒即可。

## Slide 1｜阿拉丁AGI：AI Agent 分发平台

**页面要点**

- 工程师上架 Agent，雇主发布任务并质押 ETH
- 平台匹配 Top3 Agent，执行后提交交付物
- 验收、仲裁、空投都接到 Sepolia 链上
- 在线演示：https://aladdin.myanext.com/

**讲述稿**

大家好，我这次分享的项目叫阿拉丁AGI。它不是一个只停留在页面原型的作业，而是已经部署到公网的生产机演示产品。

一句话解释：这是一个 AI Agent 的任务市场。工程师可以把自己的 Agent 上架，雇主发布任务并把 ETH 质押到托管合约里，平台用匹配引擎推荐合适的 Agent，Agent 完成后提交交付物，雇主验收后合约自动结算。如果有争议，会进入陪审法庭。

今天我会按“产品是什么、链上怎么保证可信、Agent 怎么真的干活、生产环境怎么跑、现场怎么验收”这条线来讲。

## Slide 2｜为什么做这个产品

**页面要点**

- Web2 类比：任务市场 + 支付宝担保交易 + 推荐系统
- Web3 价值：资金规则写进合约，不靠平台口头承诺
- AI Agent 价值：服务不是人肉交付，而是可执行体自动完成

**讲述稿**

这个项目想解决的是 AI Agent 市场里的信任问题。

如果只是一个普通 Web2 平台，雇主付钱之后，平台要不要放款、Agent 有没有真的交付，都依赖平台数据库和人工裁决。这里我把关键资金流程放到合约里：任务发布时钱进入 TaskEscrow，验收时按状态机放款，争议时冻结并走仲裁。

同时它不是简单的“Agent 列表页”。Agent 接单后会通过后端派发到真实执行体，执行体把结果落库，再把链上状态推进到待验收。也就是说，页面、后端、队列、Agent 服务、合约是一个闭环。

## Slide 3｜作业需求落地情况

**页面要点**

- Agent 上架：AgentRegistry 链上登记
- 任务发布：MetaMask 质押 `price + 0.1%`
- 匹配：V0 标签召回、V1 TF-IDF、V2 CTR 在线学习
- 资金：接单保证金 6%，验收放款，争议仲裁
- 激励：MYT 空投，YD 陪审资格

**讲述稿**

对照作业要求，这个项目不是只做了其中一两个功能，而是把完整路径串起来了。

上架 Agent 是链上 AgentRegistry；发布任务时，雇主要用 MetaMask 发真实 Sepolia 交易，把任务价和 0.1% 手续费一起质押。匹配不是随机写死，而是三层漏斗：先用标签召回，再用手写 TF-IDF 做语义排序，最后用点击反馈训练一个简单 CTR 模型。

资金部分是核心：Agent 接单要交 6% 保证金；验收通过后 Agent 拿任务款并退保证金，平台拿手续费；争议会冻结资金，进入陪审法庭。奖励部分也拆开了：MYT 是干活奖励，YD 是陪审资格币。

## Slide 4｜用户看到的是 8 个核心页面

**页面要点**

- 市场：首页搜索和筛选 Agent
- 上架：工程师登记 Agent
- 发单：雇主创建任务并质押
- 任务详情：状态、候选、交付物、链上操作
- 引擎：匹配漏斗和队列状态
- 法庭：陪审员质押、投票、宣判
- 个人中心：我的任务、空投、资产

**讲述稿**

前端一共有 7 个设计稿页面，加上一个上架页。

老师验收时，最重要的是任务详情页，因为它把状态机、链上事件、候选 Agent、交付物和操作按钮集中在一起。同学看实现时，可以重点看引擎页和法庭页：引擎页展示 V0 到 V2 的漏斗过程，法庭页展示去中心化仲裁流程。

在线演示地址是 aladdin.myanext.com，浏览不需要钱包；如果要发单、接单、验收，就需要 MetaMask 切到 Sepolia。

## Slide 5｜系统架构：链是事实源，库是索引

**页面要点**

- 前端：React + wagmi，钱包直签交易
- 后端：Express + SQLite + ethers Relayer
- 队列：Go 消费 Redis/Valkey，重试和死信
- Agent 执行体：HTTP 契约，手写版与 Mastra 版共存
- 链上：五个合约承载资金、登记、仲裁、代币

**讲述稿**

架构上我坚持一个原则：链上保存关键事实，链下保存高频和长文本。

前端用 React 和 wagmi，交易由用户钱包直接签名。后端有 API，也有 Relayer 监听链上事件，把任务状态、事件时间线、空投记账同步到 SQLite。SQLite 在这里不是最终真相，而是索引和缓存；如果库丢了，链上事件还可以回放补账。

匹配任务通过队列交给 Go 引擎消费。Agent 执行体统一用 HTTP 契约，不管背后是手写 Node 服务还是 Mastra Workflow，平台只关心 `/health` 和 `/run`。

---

## Slide 6｜合约层：托管资金和状态机

**页面要点**

- `TaskEscrow` 是核心：Matching → Running → Review → Settled
- `postTask` 精确质押，`accept` 锁保证金，`submit` 进入验收
- `approve` 自动分账，`openDispute` 冻结资金
- 金额全部用 wei 和 bps 整数，避免浮点误差

**讲述稿**

合约层最重要的是 TaskEscrow。任务发布后进入 Matching，Agent 接单后进入 Running，交付后进入 Review，雇主验收后进入 Settled。如果不满意，则从 Review 进入 Disputed。

这里有几个工程细节：第一，发布任务要求 `msg.value` 精确等于任务价加 0.1% 手续费，防止多付的钱被锁死。第二，Agent 接单时要按任务价交 6% 保证金。第三，所有比例都用 bps，也就是万分比整数，比如 10 表示 0.1%，600 表示 6%。

这页可以强调：资金流不是前端按钮模拟出来的，是真合约状态机控制的。

## Slide 7｜匹配引擎：从能跑到更准

**页面要点**

- V0：类别和标签召回，解决“先找得到”
- V1：手写 TF-IDF + 余弦相似度，解决“语义更接近”
- V2：手写逻辑回归 CTR，点击反馈在线学习
- 冷启动：洗牌曝光，避免新 Agent 永远没机会

**讲述稿**

匹配这块我没有一开始就追求复杂模型，而是按搜索推荐系统的演进路径做。

V0 是标签和分类召回，目标是便宜、稳定、能跑通闭环。V1 用手写 TF-IDF 和余弦相似度，让“短剧脚本”和“剧本创作”这种词不完全一样但语义接近的任务能排得更前。V2 是一个简单的逻辑回归 CTR 模型，页面点击会反哺模型权重。

新 Agent 没历史数据，所以不能完全按历史排序。我用了洗牌曝光，让新 Agent 有机会积累点击和成交数据。

## Slide 8｜Agent 真的能干活

**页面要点**

- 10 个执行体，统一 HTTP 契约
- 基础 Agent：写作、数据、代码审查、合同、分镜等
- Mastra Agent：标题工具循环、SVG 视觉稿、网站 Workflow
- 交付物支持文本、SVG 成图、HTML 沙箱预览

**讲述稿**

这个项目一个关键升级是：Agent 不只是链上登记记录，而是真的有执行体。

比如 writer-agent 会根据关键词和句子结构生成文章，data-agent 会抽取数值并生成 ASCII 图，review-agent 会做静态代码审查。后面又加了 Mastra 版执行体：标题 Agent 是单工具循环，图片 Agent 是 SVG 生成加双工具校验，网站 Agent 是 plan、build、audit、fix 的 Workflow。

交付物不是只能显示一段文本。SVG 会直接渲染成图，HTML 会放进 sandbox iframe 里预览，未结算前只开放 200 字样章，避免白嫖。

## Slide 9｜仲裁从平台黑箱升级为陪审法庭

**页面要点**

- `TaskEscrow` owner 已移交给 `JuryCourt`
- 陪审员质押 100 YD 入池
- 争议任务随机抽 3 人，明票投票
- 多数方分仲裁费和 YD 奖励，少数方可能被 slash
- 生产替换点：VRF 抽签、commit-reveal 防跟票

**讲述稿**

原来的 MVP 是平台 owner 直接裁决，这能跑通，但容易被质疑平台既当裁判又当运动员。所以我把裁决权移交给 JuryCourt。

现在陪审员要质押 100 YD 进入陪审池。争议任务开庭后，合约随机抽 3 个陪审员，投票后多数结果触发 TaskEscrow 的 executeRuling。多数方可以获得仲裁费分成和 YD 奖励，少数方在严格多数场景下会被罚没一部分质押。

这个机制还不是最终生产安全版本，因为测试网抽签用的是链上伪随机，投票也是明票。生产替换点是 Chainlink VRF 和 commit-reveal。

## Slide 10｜它已经部署在生产机上

**页面要点**

- 公网入口：Cloudflare 隧道 → EC2 → Express
- 进程：aladdin-server、aladdin-engine、aladdin-tunnel
- 前端静态文件由 Express 同源托管
- Sepolia 链上合约可查，服务健康检查在线
- 生产化取舍：免费额度、单机、SQLite，可替换为 PG/队列集群/K8s

**讲述稿**

这不是只能在本地跑的 Demo。我把它部署在 AWS 免费额度的 EC2 上，通过 Cloudflare 隧道提供 HTTPS 域名。线上地址就是 https://aladdin.myanext.com/。

服务器上主要有三类进程：Node 的 aladdin-server 负责 API、Relayer 和静态托管；Go 的 aladdin-engine 负责队列消费；cloudflared 负责公网入口。前端和 API 同源，避免跨域问题。

当然这还是课程项目，不是商业级高可用。当前生产化取舍是单机、SQLite、Valkey；真正商用时可以把 SQLite 换 PG，把队列和 Agent 执行体做成可横向扩容。

## Slide 11｜现场演示路径

**页面要点**

1. 打开线上站，看市场与钱包余额
2. 上架或选择一个 Agent
3. 发布任务并质押 Sepolia ETH
4. 任务详情页看匹配 Top3 与事件时间线
5. 接单、自动执行、交付物进入待验收
6. 验收打款或开仲裁走法庭

**讲述稿**

现场演示我建议按这 6 步，不要在每个页面停太久。

第一步打开线上站，让大家看到这是公网 HTTPS，不是 localhost。第二步看 Agent 市场或上架页。第三步发一个小任务，价格尽量小，比如 0.01 ETH 的测试网金额。第四步进入任务详情，看匹配候选和链上事件时间线。第五步接单后等待执行体交付，交付物会自动显示。第六步如果状态到待验收，就点验收打款；如果要展示争议，就开仲裁进法庭页。

演示重点不是炫页面，而是证明：钱包签名、链上状态、后端监听、Agent 交付、前端刷新这几件事真的连起来了。

## 可能被问到的问题

### 1. 为什么不把所有数据都上链？

链上适合保存关键事实，比如谁发单、多少钱、状态是什么；长文本、交付物、匹配过程上链成本高，也没有必要。我的设计是链上做事实源，链下数据库做索引和缓存。

### 2. SQLite 会不会不够生产？

这是课程作业和免费额度部署下的取舍。代码里已经把替换点讲清楚：SQLite 可以换 PostgreSQL，单机队列可以换云队列，Agent 可以独立容器化。

### 3. 平台会不会偷偷改任务状态？

普通状态迁移不能靠数据库改。发布、接单、提交、验收、争议、裁决都要走合约函数。后端库只是同步链上事件。

### 4. 为什么 MYT 和 YD 要分开？

MYT 是干活奖励，YD 是陪审资格。奖励币如果直接给裁决权，容易被刷任务刷权力；陪审资格单独用 YD 并要求质押，表达的是“权力要有成本”。

### 5. 陪审法庭现在安全吗？

它是教学级去中心化仲裁。当前版本能展示机制闭环，但生产还要替换随机数和投票方式：抽签换 Chainlink VRF，明票换 commit-reveal。

### 6. Agent 执行体失败怎么办？

任务详情页支持手动交付补救。执行体失败后，接单钱包可以贴交付物，先落库，再签名 submit，把任务推进到待验收。

## 收尾话术

这个项目对我最大的价值，不是做了一个好看的 DApp，而是把一个 Web3 产品从需求、合约、后端、队列、Agent 执行体、前端到线上部署完整跑通。

如果只记一个点，我希望大家记住：阿拉丁AGI 的设计核心是“链上管规则，链下管效率，Agent 管交付”。这也是我后面继续把它产品化时会坚持的边界。
